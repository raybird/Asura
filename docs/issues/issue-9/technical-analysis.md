# 技術方案取捨

分析日期：2026-09-14。以下為待核准範圍下的設計提案。

## 可行性與選型

| 方案 | 影響 | 判斷 |
|---|---|---|
| 沿用 SQLite，所有操作由 Daemon 授權 | 可使用交易及 scope 條件，沿用部署與錯誤處理；需加法式 schema 升級 | 建議採用 |
| 各專案新增 Markdown 記憶檔 | 可人工編輯，但要另處理並行寫入、檔案刪除與路徑安全，來源與 ID 查詢需額外格式 | 本期不採用 |

不新增向量服務：尚無語意搜尋的實際驗收需求。先以列出及 ID 查詢驗證管理能力。

## 架構影響與細節

擬新增一個記憶資料表，必要欄位為 ID、canonical workspace、content、source、created_at；source 由服務端固定 manual，不宣稱具有可信任的模型產出來源。SQL 查詢及刪除必須同時匹配 workspace 與 ID，不能只信任使用者傳入 ID。純文字內容不可當作命令執行。

既有授權與正規化分開呼叫存在路徑變動風險；實作需固定單次解析結果並以同一結果授權及存取，不得用兩次解析得到不同 scope。是否需要局部新增 auth helper，以隔離測試證據決定，不預先重構整個 Policy。

初始化只新增記憶結構，不改 Task／Cron 歷史內容；以舊資料庫副本升級、再次開啟與既有內容對照證明相容性。備份資料不因刪除 API 自動銷毀。
