# Issue 5 現況與需求分析 (Requirement Analysis)

建立日期：2026-09-13。

## 1. 業務背景與現況調查

Asura 核心於 Phase 1 至 Phase 2A 陸續完成了本地執行管線、常駐守護進程（Daemon）以及私人 Web 控制台。目前系統運作現況如下：

1. **同目錄多工並行風險**：
   - 目前 `Daemon.Submit` 與 `WorkerPool` 僅依全局最大並行數（`MaxWorkers: 2`）與全域佇列（`MaxQueue: 10`）管理任務，未對專案目錄（Workspace）建立互斥鎖。
   - 若使用者同時在 CLI 與 Web 對同一個專案發起 AI 任務，兩個任務將同時進入執行狀態，導致兩個 AI 行程在同一目錄下並發讀寫、修改原始碼或執行 git 指令，極易引發檔案寫入衝突與程式庫毀損。
2. **容量缺乏互動通道保障**：
   - 當前所有任務皆進入同一個無差別的 FIFO 佇列。一旦未來引進背景批次作業，若背景任務佔滿了所有 Worker，人類透過 CLI 或 Web 發起的即時互動任務將被迫排隊，喪失即時響應能力。
3. **無人值守自主運作缺失**：
   - 系統所有任務目前均高度依賴人類手動在終端機或瀏覽器即時點擊/輸入，無法設定週期性巡檢（如每日代碼健康檢查、定時整合測試、自動化環境探測等）。

## 2. 使用者流程與行為分析

### 2.1 CLI 動態排程管理流程
- 使用者可透過終端機執行：
  - `asura cron add -name "daily-test" -workspace "/path/to/repo" -schedule "0 2 * * *" -prompt "執行全套測試並回報結果"`
  - `asura cron list`：以表格化輸出列出所有排程之 ID、名稱、工作目錄、排程表達式、狀態（active/paused）、上次觸發時間、下次觸發時間與上次執行結果。
  - `asura cron pause <cron-id>` / `asura cron resume <cron-id>`：暫停或重啟排程。
  - `asura cron remove <cron-id>`：刪除排程定義與相關觸發關聯。

### 2.2 背景定時觸發流程
1. Daemon 常駐行程內建排程器，每秒或每分鐘依主機本地時區（Local Time）掃描資料庫中 `active` 狀態的排程。
2. 當某排程的預定時間抵達時：
   - **檢查 1（授權邊界）**：檢驗該排程之 Workspace 是否在當前 Daemon 允許的 `allowed-roots` 內。若否，回絕觸發、標記觸發紀錄為 `unauthorized`，並自動將該排程設為 `paused`。
   - **檢查 2（重疊保護）**：檢查該排程的前一次觸發任務是否仍在執行中。若是，直接略過（Skip）本次觸發，不新增任務。
   - **檢查 3（容量與通道）**：檢查當前背景 Worker 佔用數是否已達上限（預設 1 個）。若是，任務進入排隊等待，但不侵佔保留給人類互動任務的專用 Worker。
   - **檢查 4（同專案互斥）**：檢查該專案目錄目前是否已有其他任務正在執行中。若是，該任務進入 `queued` 狀態排隊，待前任務完成後自動接續執行。

## 3. 邊界與約束

- **本期邊界**：
  - 介面僅限 CLI 與 Daemon IPC，Web 端維持現狀（Web 端可透過 Task ID 查詢 Cron 產生的任務結果，但本期不實作 Web 端排程設定介面）。
  - Cron 語法嚴格遵守標準 5 欄位（分 時 日 月 星期）。
  - 排程時區統一以 Daemon 執行主機的本地時區（Local Time）為準。
