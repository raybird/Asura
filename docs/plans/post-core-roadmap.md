## 階段與依賴

| 階段 | 交付範圍 | 前置 | 不包含 | 驗收重點 |
|---|---|---|---|---|
| Phase 1.5：正式執行路徑整合 | 單一 OpenCode adapter、Daemon 可操作入口、CLI 經共同中樞提交／查詢／取消 | 既有核心已合併；新行為核准；固定版本後端契約確認 | 遠端入口、Cron、多後端、Context 壓縮 | 真實任務閉環；多 CLI 共用容量；重連可查；未知回收明確揭露 |
| Phase 2A：單一遠端入口 | Telegram 或 Web 擇一；服務端授權、接受識別、重送與結果交付 | Phase 1.5；入口選擇與權限矩陣核准 | 第二入口、Cron、完整會話平台 | 未授權零啟動；斷線可恢復追蹤；重送無重複副作用 |
| Phase 2B：容量政策與 Cron | 先定互動／背景容量及同專案寫入政策，再整合排程觸發 | Phase 2A；時區、漏跑、重疊與恢復政策核准 | 自動重跑結果未知的任務、靜默反思 | 滿載互動等待與背景進度；重複觸發去重；重啟不冒充成功 |
| Phase 3：獨立能力 | 依需求分別立項記憶、三面管線、Context 管理、多後端、其他入口 | 各能力的契約與收益證據 | 一次實作所有架構願景 | 能獨立量測收益，且不破壞授權、資源回收與副作用邊界 |

主線順序為 Phase 1.5 → 2A → 2B。Phase 3 不是單一大交付，也不必全部等待 Cron；例如基礎記憶可在共同執行路徑穩定且有明確需求後獨立立項。所有入口必須共用已核准的任務與容量契約。

## Phase 1.5：先拆解的下一項工作

詳細現況、候選驗收與工作包見 [正式執行路徑整合計畫](local-execution-integration.md)。規模 Large，風險 High；先確認權限與後端契約，再跑通最窄的 CLI → Daemon → OpenCode → 持久化結果路徑。

完成邊界是「已有可供新入口呼叫的正式執行中樞」，不是重新設計儲存、排程與程序管理。既有 shell runner 的保留方式、Daemon 不可用時的行為均須明確決策，不能靜默改變已交付 CLI 的語意。

## Phase 2A：單一遠端入口工作包

2026-09-13 補充：已建立 [Issue #4](https://github.com/raybird/Asura/issues/4)，選定本人使用的私人 Web 入口，十項驗收已核准並完成[正式拆解](../issues/issue-4/implementation-plan-decomposition.md)。下列候選敘述保留為規劃歷史，現行核准與進度以 [Issue 4 README](../issues/issue-4/README.md) 為準。

以下是規劃候選，未建立可開工的實作 Task；入口及驗收核准後才正式 decompose。

| 工作包 | 順序與內容 | 完成證據 |
|---|---|---|
| R-01 入口與授權決策 | 選一個入口；定義呼叫者到專案的服務端對應、允許操作與拒絕方式 | 核准權限矩陣；未授權請求不能指定自己的 allowed-roots，也不能啟動後端 |
| R-02 接受與重送契約 | 定義入口事件識別、去重範圍與保存期限、相同識別但不同內容的處理 | 在「接受成功但回應遺失」後重送，仍指向原任務，後端執行計數不增加 |
| R-03 最小入口接線 | 只提供提交、Task ID、查詢與取消；使用 Phase 1.5 的共同中樞 | 從選定入口完成成功、失敗、滿載與取消案例，沒有另起不受控執行池 |
| R-04 結果交付與恢復 | 定義斷線重連、傳輸長度限制與敏感內容處理；串流方式依入口選擇 | 傳輸中斷不丟失任務識別，重新查詢取得相同終態與已保存輸出 |

最大風險是遠端輸入驅動本機副作用。首要驗證為未授權對照案例；必須在入口傳輸／顯示工作前確認拒絕路徑。現有工作目錄白名單只是入口政策，不等於子程序作業系統沙箱；允許的能力邊界須明示。

## Phase 2B：先容量、後排程

| 工作包 | 順序與內容 | 完成證據 |
|---|---|---|
| S-01 容量與寫入政策 | 決定互動／背景額度、排隊／拒絕、同專案是否允許並行寫入；沿用共同 WorkerPool | 核准可量測的等待及背景進度門檻，以受控長任務滿載驗證；不只量平均值 |
| S-02 排程語意 | 決定時區、日光節約時間、漏跑、執行重疊、停用與恢復行為 | 為每個分支定義預期觸發數及任務結果，先以可控制時鐘測試 |
| S-03 觸發持久化 | 以排程識別及預定觸發時刻等已核准規則識別一次觸發，連結任務 | 在寫入觸發紀錄、接受任務與回應之間注入崩潰，無重複執行副作用 |
| S-04 Cron 接入與操作 | 使用共同授權與調度，提供查詢、停用、觸發結果追蹤 | 真實短週期 smoke test 加重啟測試；結果未知依既有不自動重跑原則處理 |

最大風險為重複副作用與背景工作佔滿互動容量。先用固定預期執行次數、已知飽和負載建立對照，才接受排程與效能量測；不需要等待生產排程窗口才能完成可自動化的驗證。

## Phase 3：分別立項，不預先建立實作 Task

| 能力 | 先完成的前置 | 首項交付 | 延後項目 |
|---|---|---|---|
| 記憶 | scope／來源／保留與刪除政策、實際檢索需求 | 可追溯的寫入與檢索，跨 scope 不外洩 | UFL 自動調權、靜默反思 |
| 三面管線 | 共同 runner 與任務事件；核准額外模型呼叫預算 | 一個固定流程的品質／成本對照 | 動態路由及多層自動修復 |
| Context 管理 | 原 P0-4：工具結果攔截、Token 用量、歷史替換的直接契約證據 | 僅對已證明可控制的部分提供最小能力 | 不受支援的透明壓縮、完整 HANDOVER |
| 多後端 | 至少兩個後端的事件、取消與失敗契約 | 明確選擇後端，保持共同結果契約 | 部分執行後自動故障轉移 |
| 其他入口 | Phase 2A 的授權、接受、去重與結果傳輸契約穩定 | 增加一個共用中樞的 adapter | 複製自己的儲存與排程機制 |

P0-4 移作 Context 相關能力的前置探測，不作為遠端基本提交或 Cron 的全域阻擋條件；若某一功能實際依賴其中能力，僅阻擋該功能。
