# Issue 建檔快速檢查清單

> 本檔由 `docs/AGENTS.md` 的 context pointer 觸發載入，與該檔同屬一套規範；`**文件版本**` 以 `docs/AGENTS.md` 為準。

`new-issue` 結束前逐項確認。

## 快速檢查清單

建立新 issue 文件時，確認：
- [ ] 已建立 `issue-{編號}/` 資料夾
- [ ] 已依任務分級建立對應文件（見「文件動態分級規範」）
- [ ] `README.md` 結尾 metadata 已填寫 `**分級**` 欄位
- [ ] `README.md` 結尾 metadata 已填寫 `**風險**` 欄位，且未由規模推導風險
- [ ] 已記錄最大風險、首要驗證、選擇理由與完成證據，並將首要驗證排在主要實作前（風險為 Low 且無特殊前置驗證時，一行收斂即可）
- [ ] 已用一次一題的流程完成澄清，且使用者已核准驗收標準；若使用 Superpowers，已記錄 `brainstorming` 調用
- [ ] 驗收標準的形式符合規模（Small 為輕量驗收條件，Medium / Large 為完整 Gherkin），且未由風險推導形式
- [ ] 採完整 Gherkin 時：核准紀錄包含核准 commit、核准來源，以及涵蓋所有現存 Scenario 的逐項核准表（或未分批時的單行省略形式；分批核准時一律使用逐項表格）；每個 Scenario 有唯一 ID、標準 Given / When / Then 與可觀察結果
- [ ] 分批核准時：已核准的 Scenario 已涵蓋核心目標的主要成功路徑與已辨識的重要失敗路徑，且每個 `待核准` 項目都有對應的待確認事項
- [ ] 採輕量驗收條件時：每項條件都有可觀察結果與可重複執行的檢查方式，並記錄核准日期與來源
- [ ] Small 且風險為 Medium / High 時：每項條件都寫出失敗路徑，至少一項覆蓋最大風險，並已記錄核准 commit（或 `待提交`）
- [ ] 測試證據的期望值來自獨立的真相來源，沒有以與被測程式碼相同的方式重算（同義反覆）
- [ ] 觀測式 AC（判準為生產環境觀測）已通過反向自檢「若這件事失敗了，這個判準會不會仍然是綠的？」，並已規劃先驗證判準本身的對照組
- [ ] 已知的未知已寫入 `## 待確認事項` 並標明狀態與影響；阻塞級未知已當場取得答案，未被降級成待確認事項
- [ ] Medium / Large：實作步驟已將每項驗收標準映射至外迴圈、內迴圈與紅綠燈證據；Small：任務清單逐步驟標注 AC 編號與驗證方式；不改變可觀察行為的任務已改記等價證據與理由
- [ ] 若有使用者明示豁免，已建立 `## Gate 豁免紀錄` 並填寫日期、豁免項目、使用者原話與殘餘風險
- [ ] 文件內容涵蓋對應章節（見「文件類型與內容規範」）
- [ ] 日期皆為系統當下日期、格式 `YYYY-MM-DD`（見「日期規範」）
- [ ] Timeline 記錄了各語意事件（建立、核准、規格修訂等）的實際日期，沒有逐步驟流水帳
- [ ] 文件連結路徑正確
- [ ] 狀態標記清晰
